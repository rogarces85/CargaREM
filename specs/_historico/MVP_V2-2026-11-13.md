## 1. Qué construye

Un portal donde el encargado de cada establecimiento sube un Excel por serie. El
sistema valida el archivo, controla el plazo y deja que el revisor apruebe la
estadística completa. Los archivos quedan guardados en el servidor para revisión
posterior.

**No se construye una base de datos fina de prestaciones.** El portal guarda el
archivo original, sus hallazgos de validación y los metadatos del envío. El
`diccionario` del MINSAL se mantiene solo como catálogo de validación.

## 2. Actores

| Rol | Alcance | Puede |
|---|---|---|
| `encargado` | Sus establecimientos asignados | Crear envío, subir versiones, enviar a revisión, corregir. |
| `revisor` | Todos los establecimientos del Servicio | Ver, observar, aprobar, descargar. |
| `admin` | Global | Todo lo anterior, usuarios, catálogos, períodos, matriz, reapertura y anulación. |

No existen los roles `consulta` ni `superadmin`. El sistema sirve a un solo
Servicio de Salud: Osorno, código MINSAL `23`.

## 3. Alcance

### 3.1 Dentro del MVP

- Login, logout y recuperación de contraseña con cuentas locales.
- Roles y permisos de la sección 7.
- Catálogos: establecimientos, series, períodos, matriz establecimiento-serie,
  plantillas, hojas, cabecera, diccionario, excepciones y snapshots.
- Envío mensual por establecimiento y período.
- Subida de un Excel por serie y por petición.
- Validación V0–V11.
- Versionado de archivos y hash SHA-256.
- Almacenamiento privado fuera de `public/`.
- Control de plazo con marca «fuera de plazo».
- Bandeja de revisión, observaciones por serie y aprobación completa del envío.
- Descarga de archivos originales y reporte de validación.
- Matriz de completitud por período y Servicio.
- Auditoría append-only.
- Notificaciones en base de datos y por correo.
- Reapertura y anulación por administración, con motivo.

### 3.2 Fuera del MVP

| Excluido | Motivo |
|---|---|
| Paquete ZIP, manifiesto y firma HMAC | Los archivos quedan en el servidor; no hay puente automático. |
| Confirmar carga en CARGAS REM | El portal termina en `aprobado`. |
| 2FA TOTP y passkeys | Se retira el segundo factor. |
| Rol `consulta` | Solo hay tres roles operativos. |
| Soporte multi-servicio | Un solo Servicio de Salud. |
| Base de datos fina de prestaciones | No se consolidan datos; solo se validan archivos. |
| Generación de archivo MINSAL | Formato fuera de alcance. |
| Migración histórica desde Access | Proyecto aparte. |
| Firma electrónica avanzada | Alcance mayor. |
| App móvil o portal de pacientes | No solicitado. |
| Colas o workers obligatorios | La validación ocurre en la petición. |

## 4. Flujo

```text
Admin
  ├─ importa catálogo
  ├─ define períodos y fecha límite
  └─ asigna usuarios a establecimientos

Encargado
  ├─ crea envío (establecimiento + período)
  ├─ sube un Excel por serie
  ├─ el sistema valida V0–V11
  ├─ corrige y sube nueva versión si hay bloqueantes
  └─ envía a revisión cuando todo está sin bloqueantes

Revisor
  ├─ abre la bandeja
  ├─ revisa archivos, hallazgos y reportes
  ├─ observa por serie, o
  └─ aprueba la estadística completa

Admin
  ├─ reabre un envío aprobado con motivo
  └─ anula un envío con motivo
```

## 5. Reglas de negocio

### 5.1 Validación

Se mantiene la cadena V0–V11 documentada en `02-DOCS/wiki/dominio/validacion-rem.md`.

| Etapa | Qué valida |
|---|---|
| V0 | Existencia, tamaño, extensión, tipo real, archivo corrupto o cifrado. |
| V1 | Nombre: código, serie y mes. |
| V2 | Cabecera: serie, año, mes, versión y establecimiento. |
| V3 | Versión de plantilla contra el catálogo. |
| V4 | Establecimiento asignado al usuario que subió el archivo. |
| V5 | Hojas obligatorias y rangos. |
| V6 | Mapeo de celdas y lectura por prestación. |
| V7 | Tipo de dato y decimales. |
| V8 | Columnas no aplicables. |
| V9 | Duplicados internos de prestación. |
| V10 | Al menos un registro válido. |
| V11 | Completitud de series exigidas por la matriz. |

**V4 cambia de contexto:** antes comparaba el Servicio de Salud del usuario con el
del establecimiento. Ahora, al existir un solo Servicio, comprueba que el
establecimiento esté asignado al usuario que subió el archivo. El código
`ENV-015`, la severidad bloqueante y el resto de la regla no cambian.

**Severidad:**

- Bloqueante: impide `validado` y `en_revision`.
- Advertencia: no impide avanzar; el revisor debe verla.
- Informativa: solo para el reporte.

### 5.2 Plazo

- `periodos.fecha_limite` es la fecha límite configurable.
- Si un período no tiene fecha límite, se usa el día 10 del mes siguiente a las
  23:59:59 de `America/Santiago`.
- Al crear el envío se copia la fecha aplicable a `envios.fecha_limite`.
- `envios.fuera_de_plazo` es booleano nullable:
  - `null`: todavía no se envió a revisión.
  - `false`: se envió dentro del plazo.
  - `true`: se envió después del plazo.
- Se calcula una sola vez, en la primera transición a `en_revision`.
- Un envío fuera de plazo **se acepta** mientras el período esté `abierto`.
- El período `cerrado` bloquea toda subida.
- El período `en_revision` solo acepta correcciones de envíos `observado`. Un
  envío nuevo requiere administrador.

### 5.3 Estados

**Envío:** `recibido`, `validado`, `con_errores`, `en_revision`, `observado`,
`aprobado`, `anulado`.

**Archivo:** `subido`, `validando`, `valido`, `con_errores`, `observado`,
`aprobado`, `reemplazado`.

`aprobado` es el estado final del MVP. No existe `cargado`.

### 5.4 Aprobación

Solo se aprueba desde `en_revision`, y solo si:

1. Todas las series exigidas tienen archivo vigente.
2. Ningún archivo vigente tiene hallazgos bloqueantes.
3. No hay observaciones abiertas.

Al aprobar:

- `envios.estado = aprobado`.
- Todos los archivos vigentes pasan a `aprobado`.
- Se registra la transición y la auditoría.
- Se notifica al encargado.

Al reabrir:

- `envios.estado = en_revision`.
- Los archivos vigentes vuelven a `valido`.
- El motivo es obligatorio y queda auditado.

### 5.5 Archivos

- Un archivo por petición.
- Extensiones: `.xls`, `.xlsx`, `.xlsm`.
- Tamaño máximo: 2 MB, validado en código.
- Se guardan en `storage/app/private/envios/{anio}/{mes}/{codigo}/...`.
- El nombre lo genera el servidor; el nombre original solo se guarda como dato.
- El reenvío crea una versión nueva; no sobrescribe.
- El hash SHA-256 identifica el contenido y evita duplicados dentro del envío.
- La descarga pasa por controlador autenticado y `Content-Disposition: attachment`.

## 9. Criterios de aceptación

1. Un encargado crea un envío y sube un Excel por serie.
2. Cada archivo se valida con V0–V11 y muestra sus hallazgos.
3. Un archivo con bloqueantes no permite enviar el envío a revisión.
4. Un reenvío crea una versión nueva y conserva la anterior.
5. Un envío enviado después de la fecha límite queda marcado «fuera de plazo» y
   se acepta si el período sigue abierto.
6. Un período cerrado rechaza subidas.
7. El revisor ve la bandeja, descarga originales y reportes, y observa por serie.
8. El revisor aprueba solo la estadística completa, sin bloqueantes ni
   observaciones abiertas.
9. Al aprobar, el envío y sus archivos vigentes quedan en `aprobado`.
10. No existen rutas, botones ni permisos de paquete o confirmación de carga.
11. No existen 2FA, rol `consulta` ni tabla `servicios`.
12. La matriz de completitud muestra el estado por establecimiento y serie, y
    distingue los envíos fuera de plazo.
13. La auditoría registra las acciones críticas y no se puede editar ni borrar.
14. `php artisan migrate:fresh --seed` y la suite completa terminan en verde.
